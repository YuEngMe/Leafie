- 종인식: 업로드 → 완료 → 생성 API → pgmq → Pl@ntNet Worker → 결과 조회 성공.
  1순위 `catalog:ocimum-basilicum`, 바질 / `Ocimum basilicum`, 신뢰도 `0.82192`.

  `HEALTHY`, `건강해 보여요`, `뚜렷한 이상 징후 없음`, 원인 후보 없음,
  `현재 관리 방법을 유지하고 정기적으로 상태를 확인해 주세요.`를 반환했습니다.
- 동일 미디어 생성 요청 재전송은 같은 작업 ID를 반환했습니다. 타인 결과 접근은 거절됐으며,
  진단 응답의 사진 URL로 받은 바이트도 원본과 같았습니다. 점수·ml 필드는 만들지 않았습니다.

사진 한 장의 성공은 질병 진단 정확도나 모든 촬영 조건을 검증했다는 의미가 아닙니다.

### 편지 전체 경로

- 신규 다이어리 → 예약 1건 → 실제 pgmq/Worker → `gpt-6-luna` 생성 성공.
  입력 644 / 출력 77토큰, 생성 시도 1회입니다. 날짜별 DB 어댑터가 실제 조회한
  `NO_DEVICE` / `UNKNOWN` 요약을 사용했으며 센서 측정값을 삽입하지 않았습니다.
- 랜덤 목표 471초, 실제 공개 472초(7분 52초). 예약 시간이나 Queue 지연을 앞당기지 않았습니다.
- 공개 전 상세 `404`, 목록 비어 있음, 미확인 개수 0, 해당 도착 알림 0건을 확인했습니다.
- 생성 후 다이어리를 수정해도 편지 ID·본문·입력 스냅샷·예약/생성 시각은 유지됐습니다.
- 공개 후 우편함 1건, 미확인 개수 1, `LETTER_ARRIVED` 알림 정확히 1건입니다.
  타인의 상세·읽음·삭제·알림 읽음은 거절됐습니다.
- 상세 조회만으로 읽음 처리되지 않았으며 명시적 읽음 후 개수 0,
  읽음 재요청은 최초 시각을 유지했습니다. 삭제와 반복 삭제는 `204`, 상세는 `404`,
  우편함에서 제거됐고 원본 다이어리는 남아 있었습니다.
- 테스트 종료 시 이번 실행의 계정·식물·사진·편지는 정리했습니다. 기존 사용자 데이터는
  수정하지 않았으며 최종 DB에서 테스트 편지 및 해당 도착 알림 잔여 0건을 확인했습니다.

전체 도구 실행은 위 기능 검증 이후 계정 탈퇴 단계에서 `401`로 종료됐습니다.
이는 5분 이내의 실제 재인증이 필요한 정상 정책입니다. 보안 조건을 완화하지 않고
도구가 탈퇴 직전에 비밀번호 로그인을 다시 수행하도록 보완했습니다. 별도 임시 계정으로
재로그인 → 탈퇴 `204` → 실제 Worker Auth 삭제 → 기존 토큰 `401`을 유료 호출 없이 확인했습니다.
15분 대기 중 서명 URL 만료를 정리 성공으로 오인하지 않도록 삭제 직전 새 URL도 발급합니다.
이 보완까지 포함한 도구 전체를 유료로 다시 실행한 것은 아닙니다.
공개 전 검사 중 API 결과가 달라지면 DB의 실제 공개 여부를 다시 확인해, 공개 순간의
조회 경합을 잘못된 조기 노출로 보고하지 않습니다. 미공개 상태의 실패는 계속 거절합니다.
이 경계의 무과금 회귀 테스트도 포함합니다.

### 재실행

API/Worker와 같은 로컬 `.env`를 사용합니다. `LETTER_GENERATION_ENABLED=true`에서
`--letter`와 `--allow-paid`가 없으면 실행을 거부합니다. 사진 형식은 계정 생성 전에 검사하고,
JPEG를 Pillow가 `MPO`로 표시하는 경우에도 API와 동일한 파일 시그니처로 판별합니다.

```sh
cd backend
python -m tools.smoke_live --allow-shared-dev --allow-paid --letter \
  --photo /absolute/path/to/real-plant.jpg --timeout 180 --letter-timeout 1200
```

이번 총 실제 호출은 Pl@ntNet 1회·Kindwise 1회·OpenAI 3회입니다. OpenAI는 초기 사진
판별 오류로 중단한 실행의 편지 1회, 전체 경로 1회, 아래 시점 보완 확인 1회입니다.
실제 ESP 측정값이 포함된 편지·6개 성격 전체의 실출력·iPhone 화면은 미검증이며,
FCM/APNs는 제외합니다. 별도 배포 서버에 이 로컬 변경을 반영한 기록은 아닙니다.

## 수정 및 회귀 검증

- 삭제된 식물·삭제 중/실패한 계정·삭제된 미디어의 진단/종인식 작업 시작을 차단합니다.
- 외부 응답이 도착한 뒤에도 활성 계정·식물·미디어를 다시 확인합니다. 삭제 이후 결과와
  진단 완료 알림을 새로 저장하지 않습니다.
- 진단은 기존 편지·삭제와 같은 계정 → 식물 → 하위 데이터 잠금 순서를 사용합니다.
  진단 재시도·취소의 조회 잠금도 이 순서에 맞춰 역순 잠금을 피합니다.
- 종인식 완료·실패는 행 잠금 아래 상태를 확인하여 완료 결과를 실패로 덮어쓰지 않습니다.
- `test_ai_workflow_postgres.py`는 실제 PostgreSQL에서 삭제·늦은 응답·동시 삭제·중복 완료와
  진단 결과/알림 트랜잭션 rollback을 확인합니다.
- 같은 파일의 HTTP 흐름 테스트는 presign → 업로드 완료 → 진단/종인식 생성 → Worker →
  상세 조회, 요청 재전송·타인 접근 거절을 검증합니다. 이 테스트의 Storage·Queue·Provider는
  테스트 대역이며 실제 Supabase Storage/pgmq까지 연결한 검증과 구분합니다.
- CI에서 AI·편지·관리 일정·센서 테스트 전용 DB를 모두 준비합니다. 기존 센서 DB 테스트가
  환경변수 누락으로 skip되지 않게 합니다. 테스트는 localhost의 지정된 전용 DB만 허용합니다.
- 진단·종인식의 실행 lease와 토큰 검증으로 중단 후 재선점, 늦은 결과/실패 무시,
  동시 선점 방지, DB 기반 재시도 한도를 적용합니다. 활성 lease의 중복 수신은 큐에서
  지연하며 실제 선점 횟수를 소모하지 않습니다.
- heartbeat 대기 만료와 handler의 `TimeoutError`를 구분합니다. Worker 취소 시 실행 중인
  handler도 취소하며 복구 메시지를 archive하지 않습니다.
- 신규 migration `b7e3a91d6f20 -> d2f6a83b9c10`으로 두 테이블에
  `lease_token`, `lease_until`, `attempt_count`를 추가합니다. 최소 기존 테이블과
  PROCESSING/COMPLETED 행을 둔 임시 DB에서 증분 upgrade와 기본값/상태 보존을 확인합니다.
- 로컬 PostgreSQL 17의 AI·편지·관리 일정·센서 전용 DB를 사용한 전체 테스트:
  **506 passed, 0 skipped**. Starlette 테스트 클라이언트 의존성 deprecation 경고 1건.
  Ruff, `pip check`, `git diff --check` 통과.

| 편지 소비 인터페이스 | `LetterSensorSummary.read(plant_id, diary_date) -> str`, 최대 4000자·오류 처리 있음 | 기존 Worker/Provider 테스트 유지 |
| 누적 조도·급수 판정 | 측정값에서 해당 날짜 결과를 산출하는 방식·임계값·확정 결과 조회 계약 없음 | 계산을 임의 구현하지 않음 |
| 홈 상태·센서 알림 | 책임 경계는 있지만 구체 상태 산출·이벤트 중복/복구 규칙 없음 | 임의 상태·알림을 만들지 않음 |

인터페이스가 있다는 것과 실제 요약 조회 구현이 준비됐다는 것은 다릅니다.
`UnconfiguredLetterSensorSummary`는 유지하며 `LETTER_GENERATION_ENABLED`를 켜지 않습니다.
센서 요약이 준비되면 기존 어댑터 자리에 연결하면 됩니다.

## AI 복구 배포 순서와 한계

1. 구 버전 Worker를 모두 종료합니다. 구 Worker는 실행 토큰을 확인하지 않으므로 신·구
   버전을 섞어 실행하면 늦은 응답 보호가 성립하지 않습니다.
2. 대상 DB를 확인하고 `alembic upgrade head`로 `d2f6a83b9c10`을 적용합니다.
   이번 검증은 임시 로컬 DB만 사용했으며 공유 Supabase DB에는 아직 적용하지 않았습니다.
3. 새 API/Worker를 함께 반영합니다. 외부 응답 필드는 그대로지만 ORM은 새 컬럼을 사용합니다.
4. 살아 있는 큐 메시지는 재전달 시 복구됩니다. 과거 구 버전이 이미 archive한 메시지는
   자동 복원하지 않습니다. 장시간 PROCESSING 행과 큐를 대조하고, 실제 실행이 없음을
   확인한 건만 동일 resource_id로 기존 작업을 재enqueue해야 합니다. 유료 재호출 위험 때문에
   migration에서 전체 AI 작업을 일괄 재발행하지 않습니다.

DB/큐 장애로 선점 자체가 불가능하면 메시지를 유지하며 재시도합니다. 실제 AI 선점은
`worker_max_attempts`로 제한합니다. 프로세스 SIGKILL의 운영 환경 검증 대신 로컬 실제
handler의 취소, lease 만료 후 재전달, 동시 재선점, 이전 토큰의 모든 쓰기 차단을 검증했습니다.

- 외부 푸시 수신: 대회 범위에서 제외. 인앱 알림 기능은 유지합니다.
