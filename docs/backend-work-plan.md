# 백엔드 작업 계획

## 1. 역할 경계

- 공통 백엔드: 인증 연결, 프로필, 식물, 미디어, 다이어리, 편지, 일정, 진단, 알림,
  Queue와 Worker
- Flutter: 화면, 권한, 로컬 등록 초안, Supabase Auth SDK와 딥링크
- 센서 담당: 장치 연결, 원시 데이터, 일별 집계, 습도·조도 판정과 센서 이벤트
- 공통 연동: 센서 담당 결과를 홈 표정, 편지 입력과 알림에 연결

AI 채팅과 Tool Calling은 더 이상 작업 대상이 아닙니다.

## 2. 권장 작업 순서

### 1. 계약 정리와 migration

- 삭제 대상: 채팅·Tool Calling·AI action, 홈 메모, 컨디션 점수, 가지치기·자유 할 일
- 변경 대상: 식물 등록 필드, 다이어리 제목·날씨, 관리 종류
- 추가 대상: `letters`와 편지 상태·인덱스·RLS
- 기존 운영 데이터의 보존·삭제·변환 방식을 migration에 명시

### 2. 식물·홈 계약 정리

- 등록에서 장식·화분·위치·컨디션을 제거하고 분갈이 날짜를 nullable로 변경
- 식물 정보 수정은 애칭·장소 별명, 꾸미기는 컬러·헤어만 허용
- 홈 응답을 D+, 시간대 배경, 성격 대사, 우편·알림 개수 중심으로 변경
- 센서 결과는 임시로 nullable 경계 또는 별도 합성 계층만 마련

### 3. 다이어리 v2

- 날씨, 제목, 본문, 사진 한 장과 식물·날짜 unique 구현
- 컨디션 입력과 월별 통계 제거
- 생성·수정과 미디어 교체 테스트

### 4. 편지 생성

- 다이어리 최초 생성과 `PENDING` 편지 예약을 한 트랜잭션으로 구현
- 5~15분 랜덤 `scheduled_at` 생성
- `LETTER_GENERATION_RUN` Worker와 OpenAI provider 구현
- 생성 직전 최신 다이어리와 센서 담당 일별 요약 조회
- 완료 편지 불변, 중복 요청·Queue 재전달·Worker 재시작 검증
- 일시 오류 재시도와 영구 실패 상태 저장

### 5. 우편함과 알림

- 편지 목록·상세·읽음·삭제·미확인 개수
- 편지 도착 알림과 푸시 outbox 연결
- 삭제 확인 뒤 편지만 숨기고 다이어리는 유지
- FCM Fake 발송 테스트 후 APNs 키 등록 시 실기기 검증

### 6. 캘린더 정리

- 관리 종류를 물주기·분갈이·비료로 제한
- 물주기·분갈이 반복, 비료 일회성 정책 유지
- 월·주 범위 조회와 과거 완료 처리
- 가지치기·컨디션·자유 할 일 코드와 데이터 정리

### 7. 진단 분리

- 진단 요청에서 conversation ID 제거
- 독립 이력·상세·재시도 흐름 검증
- Kindwise 실제 호출과 Fake provider 회귀 테스트

### 8. 통합과 삭제

- 식물 삭제 시 다이어리·편지·일정·진단·알림·미디어 정리
- 회원 탈퇴 Worker와 새 FK의 삭제 순서 검증
- 등록부터 편지·진단·알림까지 실제 사용자 E2E 수행

## 3. 완료 조건

### Auth·프로필

- 이메일 인증, 비밀번호 재설정 딥링크와 Naver·Kakao·Apple 로그인 검증
- OAuth 신규 사용자의 닉네임 완료 전 보호 화면 진입 차단
- 프로필 사진·한 줄 소개 없는 계약 유지

### 식물 등록·홈

- 23종 검색과 사진 후보 순회가 동작
- 등록 요청 재전송에도 식물과 반복 일정이 한 번만 생성
- 대표 사진 재사용과 로컬 초안 복원 확인
- 홈의 D+, 배경 구간, 성격 대사와 읽지 않은 개수 검증

### 다이어리·편지

- 다이어리당 편지가 정확히 한 통 생성
- 도착 예약이 5분 이상 15분 이하
- 생성 전 수정은 최신 본문, 생성 후 수정은 기존 편지 유지
- 빈 후보, OpenAI 인증 실패, timeout·429·5xx, 재시도 소진 검증
- 다른 사용자의 다이어리와 편지 접근 차단

### 일정·진단·알림

- 캘린더에 세 관리 종류만 노출
- 과거 완료와 반복 다음 회차가 원자적으로 반영
- 진단이 채팅 없이 독립 수행되고 결과 확률은 Provider 값을 사용
- 알림 읽음과 푸시 대상 수집이 사용자 설정을 존중

## 4. 테스트 기준

- 서비스 단위 테스트: 인증 실패, 소유권 위반, 경계 날짜, 중복 요청
- Worker 테스트: 원자적 선점, 외부 API 실패, 재시도, 최종 실패, 중복 Queue 전달
- Repository 통합 테스트: unique, FK, RLS, 트랜잭션 rollback
- API 통합 테스트: 응답 schema와 오류 코드
- 실제 provider smoke test: Pl@ntNet, Kindwise, OpenAI 편지 생성
- iOS 실기기 E2E: 사진 권한, 딥링크, foreground/background/종료 푸시

## 5. 브랜치와 PR

- migration과 모델·서비스 변경은 같은 기능 PR에 포함합니다.
- PR에는 제거·변경된 API, migration 적용·rollback, 테스트 결과를 적습니다.
- 센서 담당 계약이 확정되기 전 센서 구조를 추측해 공통 migration에 넣지 않습니다.
- merge 전 `alembic heads`가 하나인지 확인하고 공유 DB 적용 순서를 합의합니다.
